## A. 产品范围

### TO-01 对话是单轮的，但内部轨迹是多步的

这两件事必须分清，否则看起来自相矛盾。

- **决定**：
  - **对话单轮**：用户视角只有一问一答，不保留跨轮历史。
  - **内部多步**：一次请求内部是一个 ReAct 循环，`plan → search → reflect → …（≤3 轮）→ synthesize`。
- **为什么单轮对话**：评测单元因此极简——一个输入对应一个可判定的输出。多轮对话的评测要评「跨轮上下文是否被正确继承」，是另一个产品。
- **为什么内部多步**：单跳检索答不了需要两处证据的问题；而且显式的多节点结构带来两个评测上的收益——每个节点的 prompt 可独立版本化，policy 违规可归因到具体节点。（原文这里还有第三条「`max_loops` 成为一个真实的成本/质量权衡杠杆」。Step 3 把 `max_loops` 砍出了杠杆集合，见 [TO-06](#to-06-被版本化的杠杆是四个)，所以这条收益没了——循环上限仍然是个真实的权衡，只是不再由界面暴露。）
- **代价**：每个问题的 LLM 调用从 2 次涨到 3–5 次，**配额压力和端到端延迟都翻倍**；Step 1 预算从 2 小时涨到 2.5 小时；Step 2 必须支持对**轨迹**下断言（循环次数、是否检索过、`terminated_by`），不只是对最终文本下断言。
- **仍然的缺口**：跨轮对话的行为漂移看不见。这仍是本项目最大的能力缺口，只是「单次请求内的多步轨迹」这一半已经补上了。

### TO-02 语料与检索刻意做薄

> Step 3 合并：吸收了原 TO-03（语料是本地静态快照）。两条是同一个取向——**检索质量不是本项目的题目，change safety 才是**。

- **共同的为什么**：做 RAG 会引入一整套不同的评测词汇（recall@k、chunk 归因），把时间吃光还模糊了主线。语料新鲜度同理与本项目无关，而且离线可复现对评审更友好。

**检索用 grep，不做 RAG**

- **决定**：`search_docs` 就是对本地文件的关键词检索，无 embedding、无向量库、无 reranker。
- **代价**：召回明显差，概念性问题经常检索不到好片段。
- **这个代价反过来是收益**：检索不到时模型是否老实说「不知道」，正好是 P3（Refusal）最好的考场。而且 grep 弱 ⇒ 工具描述对模型行为的影响被放大 ⇒ [TO-06](#to-06-被版本化的杠杆是四个) 那个 demo 更有说服力。

**语料是本地静态快照**

- **决定**：一次性抓取 Luma Learning Center 的 39 篇文章存成本地 markdown，之后不再更新。抓取是构建期脚本，运行时只读本地文件。
- **代价**：不做增量更新、不做失效检测。文档改版后我们的答案会过时而系统不自知。
- **相关**：`corpus_hash` 进了结果缓存的键（[TO-16](#to-16-seed-用预计算结果直接入库不做-fixture-replay-层)）。少了它，缓存会拿旧语料下的行为冒充现在的行为。

### TO-03 检索用 grep，不做 RAG

> 已并入 [TO-02](#to-02-语料与检索刻意做薄)。编号保留：`design_high_level.md` 和 `design_step1_ai_app.md` 都引用了它。原本独立成条，是因为「不做 RAG」和「语料不更新」在规划时是两个不同时间点的决定。

### TO-04 不做认证、多租户、RBAC

- **决定**：假设单团队单用户，没有登录。
- **代价**：不能演示「谁改了什么需要谁批准」这类真实的变更治理。审计日志仍然记录 actor 字段，只是值是硬编码的。

## B. 架构与运行时

### TO-05 模型这条轴整个不动

> Step 3 合并：吸收了原 TO-28（judge 用同一个模型）。TO-28 的正文第一句本来就是「这是 TO-05 的延伸」。

- **共同的为什么**：**judge 模型必须 pin 住**。judge 模型一换，历史基线全部失效，评测就没有可比性了——而这个项目的全部价值建立在「两次评测结果可比」之上。

**`model` 不进版本化配置**

- **决定**：`model` **不是**版本化杠杆之一。chatbot 和 judge 都用 `.env` 里那一个模型。
- **为什么**：demo 用我个人的 API key，成本自己承担，所以选最简单最便宜的模型。
- **两个衍生决定**（详见 [design_step1_ai_app.md](design_step1_ai_app.md) 第 5 节）：
  - **`.env` 里填具体版本号，不用 `-latest` 别名**，并把响应里的 `modelVersion` 记进每条 trace。别名会漂，而漂移会伪装成「我的 prompt 改动导致了行为变化」，是所有风险里最难排查的一种。这条原则不止于模型：Step 3 顺手把 `Dockerfile` 里的 `uv:latest` 也改成了按 digest pin——一个论点如果只在一个地方用，它就只是个论点。
  - **成本用本地价格表算，不用 LiteLLM 的 `completion_cost()`**。别名或新模型查不到价格会静默返回 0，而成本是高光 demo 的一半说服力。
- **代价**：失去「换个便宜模型」这条现实中最常见的行为变更动机，成本轴的变化幅度也变小了。
- **但保留了什么**：成本和延迟仍然是一等公民指标，因为**是否调用检索工具本身就显著影响成本和延迟**。这反而让 [TO-06](#to-06-被版本化的杠杆是四个) 的 demo 更漂亮：模型不检索之后，成本降了、延迟降了、答案还很流畅——**看起来像一次优化，实际是一场灾难**。这比换模型省钱的故事更有冲击力。
- **后续**：配置对象里加回 `model` 字段即可，评测/审阅/灰度/回滚流水线一行都不用改。

**judge 用与 chatbot 完全同一个模型**

- **决定**：judge 直接读 `.env` 的 `MODEL` 和对应的 key，与被评测的 chatbot 同一个模型同一个 key，**不给 judge 单独配置**。
- **为什么**：省掉第二套模型配置、第二个 key 和「judge 用哪个模型」这个决策。这一步的重心是把评测流程跑通，不是把评测做到可发表的严谨度。
- **代价**（两条独立的问题，都要在 `APPROACH.md` 明示，不能含糊成一句「为了简单」）：
  1. **模型漂移作废历史基线**。生产环境必须把 judge 模型跟被评测模型解耦并独立 pin 住——否则「顺手升级一下 chatbot 模型」会同时把整个历史基线换掉，而且不留痕迹。
  2. **自我评价偏袒（self-evaluation bias）**。让模型判自己的输出已知会系统性偏松。这是除了 [TO-10](#to-10-评测输出的形状逐条判定确定性做门禁judge-只做参考) 的「会抖」之外，judge 判定不能当 blocking 门禁的**第二个**理由。
- **缓解**：judge 判定只做 advisory——`BenchResult.passed` 只由确定性检查决定，**代码上根本不读 `verdicts`**。这样「blocking vs advisory」不只是文档里的说法。
- **推翻条件**：要做严肃评测就必须换一个不同家族的模型当 judge，并把它的版本号写进 `BenchRun`（现在没记，这是个已知缺口）。

**和 [TO-31](#to-31-model-跨-provider-可换但仍然不是版本化杠杆) 的分工**：Step 3 让 `MODEL` 支持 `anthropic/` 和 `openai/`，看起来像推翻这一条，其实不是。`MODEL` 一直是**部署级环境变量**；这一条说的是它**不进版本化配置**。版本表的 schema 一个字段都没改，这是最直接的证据。

### TO-06 被版本化的杠杆是四个

> Step 3 后期修订：原本是六个。`temperature` 和 `max_loops` 砍掉了，退回代码常量。原标题「被版本化的杠杆是六个」，改了标题但编号不变。

- **决定**：版本 = `plan_prompt` + `reflect_prompt` + `synthesize_prompt` + `tool_description`。`config_hash` 是全部四项规范化后的 sha256。存成一个 JSON 列而不是四个字段，这样加杠杆不用改表。
- **为什么**：题面列的七个杠杆想说的是「变更单位是一份行为配置，不是一段 prompt」。
  - **三个节点的 prompt 分别版本化**，而不是拼成一个大 prompt——这是 diff 可归因的前提，断言失败时能直接指出该改哪个节点。
  - **`tool_description` 纳入版本**是让产品不退化成 prompt 管理工具的关键，而且它解锁了本项目最强的 demo：**改一行工具描述，模型就不再检索、开始凭空编造，而 prompt 的 diff 是空的**。它也是四个里唯一一个语义上不属于「prompt 行为」而属于「工具用法」的。
- **代价**：版本对象比原来大得多，diff UI 必须按节点分组渲染，否则一屏塞不下。杠杆里仍然没有 model / retrieval / post-processing。
- **缓解**：在 `APPROACH.md` 里说清楚流水线对变更类型不可见，加杠杆是加字段而不是改架构。

**为什么砍到四个，以及砍掉之后失去了什么**

砍的理由是 demo 的注意力预算，不是这两个杠杆不成立。五分钟里能讲清的东西有硬上限，而六个杠杆**单位屏幕面积的说服力不等价**：`temperature` 和 `max_loops` 在 demo 里能贡献的是「你看，数值型杠杆也支持」，而**这句话版本表的 schema 已经说过了**——`BehaviorConfig` 是一个 JSON 列，加字段不改表。用两个控件重复说一遍，占的是讲 `tool_description` 的时间。

代价里有一条必须点明，因为它推翻了本条原来的一段论证：

- **原文有一句是「`max_loops` 补回了 [TO-05](#to-05-模型这条轴整个不动) 砍掉的成本/质量权衡轴」。这句话现在不成立了。** TO-05 把 `model` 移出杠杆，代价是失去最常见的那条成本/质量轴，`max_loops` 当时被拿来补这个洞（调低更便宜更快但 `exhausted` 率上升，调高召回更好但成本延迟线性涨——教科书级的需要人判断的权衡）。**现在这个洞重新开着。** 四个杠杆全是文本，没有一个数值型的。诚实的说法：这个产品现在管的是**用文字描述的行为**这一类变更；用数字调的那一类，机制上支持而界面上没有入口。
- **`temperature` 不能再按版本实验。** 想比较 0.2 和 0.7 得改代码重新部署，正是这个产品要消灭的那种流程。
- **失去一个「同一份配置跑两次结果不同」的现成解释入口。** 以前可以直接指 `temperature`；现在得靠文档说明它 pin 在 0.2。
- **不给这两个做 UI signpost。** 这跟灰度（[TO-09](#to-09-灰度按-session_id-确定性分桶运行时已通控制面不做)）、tag 查询（[TO-15](#to-15-不做-production-monitoring-和-alerting)）性质不同：那两个是「这次不做、以后要做」，所以摆在界面上预告；这两个是**决定不作为杠杆存在**。给一个已经想清楚不要的东西留预告位，等于承诺一件不打算兑现的事。
- **落点**：`agent.llm.TEMPERATURE = 0.2`、`agent.graph.runner.MAX_LOOPS = 3`。都是代码常量而**不是环境变量**——一个在两台机器上悄悄不同的旋钮，会让两边的评测结果不可比，而这正是这个项目要消灭的失效模式。judge 的 `JUDGE_TEMPERATURE = 0.0` 是另一个有理由的值，所以 `llm.call()` 保留 `temperature` 参数但给默认值。
- **连带**：`config_hash` 全变（baseline `c64bbc62a755c53d` → `ea2580ac6b707853`），[TO-16](#to-16-seed-用预计算结果直接入库不做-fixture-replay-层) 的 seed fixture 必须重跑重导。数据库里带六个字段的历史 `Version` 行不会坏（Pydantic 默认忽略多余字段），它们存的旧 hash 记录的确实是当时那份配置。

### TO-07 prompt 放在 critical path 上

- **决定**：生效版本的解析放在**线上请求路径里**。chatbot 每次请求都通过 `config_client` 拿当前该用哪个版本，绝不把 prompt 编译进代码或从静态文件读死。
- **为什么**：**这是能做 gradual traffic rollout 和即时回滚的唯一前提。** 如果 prompt 写死在代码里，切流量就必须重新部署一次，实验根本没法做，「一点一点放量」这个核心能力就不存在。
- **代价**：控制平面成了业务的**运行时依赖**——每个请求多一次配置读取，并且多了一类故障模式（配置读不到就服务不了）。
- **缓解**：进程内 5 秒 TTL 缓存，加上 console 写操作调用 `invalidate()` 让改动立即生效。
- **原本还有 fail-open 到 last-known-good，现在去掉了**（见 [TO-22](#to-22-交付形态能一口气读完零构建跑起来)）：合并成单进程之后这只是一次本地 SQLite 读，没有「只有配置挂了」这个故障模式，那个分支是永远跑不到的死代码；而且**配置读失败时静默沿用旧配置，恰好制造了这个产品要消灭的那种情况**——行为和你以为的不一致且毫无信号。**以后真拆成两个进程、这一跳变成 HTTP 调用时，fail-open 就该加回来。**
- **明确不做**：分布式配置中心、配置 CDN、多 region 一致性。

### TO-08 代码边界与进程边界是两件事

> Step 3 合并：吸收了原 TO-21（一个进程托两个 app）。TO-21 的正文最后一句本来就是「修正了 TO-08 里『两个独立服务』的说法」。

**代码边界：两个 app 互不依赖，契约提到共享包里**

- **决定**：`apps/chatbot` 和 `apps/console` 是两个独立的代码单元，共享 `data/app.db` 一个 SQLite 文件。两者都依赖 `packages/behavior_core` 和 `packages/agent`，**互相不依赖**。
- **为什么需要共享包**：chatbot 需要「当前该用哪个版本」和「怎么写 trace」，而版本和实验是 console 的概念。如果这些定义住在 `apps/console/` 里，chatbot 就得反向依赖 console——**服务端依赖控制台，方向完全错了**。把契约提到 `packages/behavior_core`，方向就对了，而且它就是 [TO-07](#to-07-prompt-放在-critical-path-上) 说的那个 SDK 接缝的实体：现在 `config_client` 读同一个 SQLite，生产里换成 HTTP 加磁盘缓存，chatbot 代码一行不用改。
- **Step 2 追加的一层**：ReAct 内核下沉到 `packages/agent`。理由更硬——console 跑 benchmark 用的必须是 chatbot 服务用户时跑的**同一份代码**，内核留在 chatbot 里就得让 console import chatbot，那会让「benchmark 测的就是 production 的行为」从结构事实退化成一句声明。
- **规则的边界（Step 3 澄清）**：这条规则管的是 **Python import**，不管 HTTP。console 的页面 fetch `/api/conversations`（属于 chatbot 的端点）没有越界——两个 app 由同一个进程挂在同一个 origin 下。`scripts/check_assertions.py` 扫的是 import，所以它不会误报，也不该改。
- **代价**：配置解析走的是**数据库读**而不是对 console 的 HTTP 调用，所以「控制平面整个挂掉、chatbot 还活着」这个场景没法真正演示（数据库是两者共同的依赖）。
- **用可执行的东西守住依赖方向**：写在文档里的规则会被忘记，`check_assertions.py` 里的那条扫描不会。

**进程边界：默认合并成一个服务，拆分是部署决策**

- **决定**：目录分开、包边界分开、依赖规则由断言守住，但**默认由一个 FastAPI 进程同时挂载**。合并入口 `apps/server/src/server/main.py` 只有十几行，是唯一允许同时 import 两个 app 的模块。
- **为什么**：
  - **回滚能真正即时生效。** 两个进程时 console 改了版本没法让 chatbot 的进程内缓存失效，回滚要等最多 5 秒 TTL；合并后「点回滚 → 下一个请求就是老版本」。**这是 demo 里体感差别最明显的一处。**
  - 消掉 SQLite 多进程写竞争（WAL 仍然开着，因为分开跑仍是被支持的部署方式）。
  - 评审只需要一个容器、一个端口、一条命令。
- **代价**：没有进程级故障隔离，console 崩了会连带 chatbot。
- **为什么这个代价可接受**：**拆分只需要改部署配置，不需要改代码**——两个独立入口本来就存在，Step 1 用的就是 chatbot 那个。

### TO-09 灰度按 session_id 确定性分桶；运行时已通，控制面不做

- **决定**：`hash(experiment_id:session_id) % 100 < rollout_pct` 决定走哪个版本。同一 session 始终看到同一版本。
- **为什么加盐**：盐是 experiment id，为的是让连续两个实验重新洗牌。没有盐，同一批用户每次都落在同一侧，第二个实验的结果会被第一个污染。
- **代价**：不做统计显著性检验。几十条流量下那个 p 值没有任何意义，假装有反而是误导。
- **缓解**：UI 上明示每个 arm 的 n，样本不足时直接标注，不给出「哪个更好」的结论。

**Step 3 收口：运行时已经在跑，控制面明确不做**

写 Step 3 的时候我先读了一遍代码，结果比原本准备写的「以后做起来很简单」硬得多。已经实现并且**每个线上请求都在走**的部分：`config_client.resolve()` 里查「有没有 running 的 Experiment」、`_bucket()` 的加盐分桶、`rollout_pct` 比较、选 candidate / baseline、`arm` 和 `experiment_tag` 打进响应和 `Conversation` 行（后者建了索引）。

缺的只有两样：**没有任何地方能创建 `Experiment` 行**（所以 `rollout_pct` 永远用不上），以及**没有放量策略**（健康度阈值、ramp 节奏、自动回滚触发条件，连设计都没有）。

- **UI 形态**：console 左栏一个 **Rollout** 区块，里面是**真实但禁用**的控件——`rollout_pct` 滑块、candidate / baseline 版本选择器（填的是真实版本列表）、tag 输入框。不是一段「Coming soon」文案。
- **为什么是禁用控件而不是文案**：文案只能被读，控件能被**看懂形状**。看到滑块和两个版本选择器，立刻知道这个功能的输入是什么、粒度是什么；读一段「以后会支持按比例放量」什么都不知道。而且禁用控件把「缺的是控制面」变成了视觉上的字面事实——控件在那儿，就是点不动。
- **为什么不真的插一行 `Experiment` 演示分桶**（诱惑很大，几乎零代码）：
  1. **它会真的切流量。** demo 里演示「Activate 立即改变行为」时会有一半 session 落在 candidate 上，**两个演示互相污染**，而 Activate 那个是整个项目最核心的 demo。
  2. **没有放量策略的灰度是个玩具。** 灰度的价值不在「能分流」，在「分流之后靠什么信号决定继续放还是回滚」。只演示分流会让人以为难的部分已经解决了。
  3. **它会让说明文案变成谎话。** 一边说 control surface is missing，一边偷偷手插一行让它跑起来。
- **验收上钉了一条**：`select count(*) from experiment` 必须是 0。

## C. 评测方法

### TO-10 评测输出的形状：逐条判定、确定性做门禁、judge 只做参考

> Step 3 合并：吸收了原 TO-11（确定性检查优先）和原 TO-12（judge 非确定性）。三条是同一个命题的三个面。

- **共同的命题**：**评测的输出必须是可行动的逐条判定，而且能当门禁的那部分必须是确定性的。** 这是整个评测方法的骨架，也是 demo 主线 2。

**逐条 policy 判定，不输出总分**

- **决定**：judge 返回结构化 JSON，逐条给 pass/fail 加理由。**不产出 0-1 总分，不做平均。**（Step 2 把「逐条」精确成「逐条 case 手写的 dynamic expectation」，每条挂一个 policy 标签用于聚合。）
- **为什么**：`0.82 → 0.85` 不告诉你任何事，而「case 3 的 P3 从 pass 变成 fail，理由是编造了一个不存在的导出格式」直接可行动。平均分还会把致命违规稀释掉。
- **代价**：没法一眼比较两个版本「谁总体更好」，必须看 diff。**这正是想要的效果**——上线决策本来就不该被压缩成一个数字。

**确定性检查优先，judge 只兜底**

- **决定**：能用规则判的绝不调 judge。引用用「是否包含真实存在的文章标题」匹配（[TO-30](#to-30-引用检查用贪心最长匹配不按分隔符切分)），P5 用词数，P6 用 system prompt 片段匹配，外加一条**「这次到底调了 `search_docs` 没有」**的确定性断言（读 trace 里 search 节点的 `tool` 字段）。只有 P1 grounding、P4 拒答是否恰当、P7 语气交给 judge。
- **为什么**：便宜、快、可复现，而且规则类断言可以设成 blocking 门禁而 judge 不行。
- **落地形式**：这条分工在数据集里变成两段显式结构——`observations`（fixed，确定性，blocking）与 `expectations`（dynamic，judge，advisory）。同一个事实可以两边都出现但角色不同：`search_docs` 的调用由确定性检查出判定，同时作为上下文喂给 judge，让它的语义判定能说出「这句话没出处，因为这一轮根本没检索到证据」。
- **代价**：规则会有假阴性（换一种引用写法就匹配不上）。
- **缓解**：引用匹配基于真实文章标题表做模糊匹配，而不是要求固定格式。

**judge 本身非确定性，只对翻转的 case 重跑**

- **决定**：judge 判定会抖。只对**发生 pass↔fail 翻转**的 case 重跑 k 次取多数，UI 上标注置信度低。judge 类断言默认不作为 blocking 门禁。
- **为什么**：全量多次采样太贵太慢，而真正需要确认的只有翻转的那几条。
- **代价**：非翻转 case 的判定只有单次采样，可能藏着噪声。
- **Step 2 的实际状态**：「翻转重跑」**推迟了**——它本质是跨 run 比对，属于 [TO-25](#to-25-simulation-只单跑不并排对比基线) 砍掉的对比范畴。本步 judge 判定只做单次采样并在 UI 标注 `n=1`。
- **后续**：人工标注 20 条，度量 judge 与人的一致率——一致率低就不该信它的分。

**代码上的落点**：`BenchResult.passed` 只读 `observations`，**根本不读 `verdicts`**。`scripts/check_assertions.py` 把 `judge.run` 打桩成全 fail，跑真实的 `bench._run_case`，断言 `passed is True`。「blocking vs advisory」因此是可执行代码保证的，不是文档里的说法。

### TO-11 确定性检查优先，judge 只兜底

> 已并入 [TO-10](#to-10-评测输出的形状逐条判定确定性做门禁judge-只做参考)。编号保留：三份设计文档共 4 处引用。原本独立成条，是因为规划时「输出什么形状」和「谁来判」是两个先后决定。

### TO-12 judge 本身非确定性，只对翻转的 case 重跑

### TO-13 golden dataset 的形状：3 条、YAML、不入库

> Step 3 合并：吸收了原 TO-14（数据集存 YAML）。两条都在回答「数据集长什么样」。

**只有 3 条 case**

- **决定**：原计划 10 条，**Step 2 砍到 3 条**（你定的）：`off-topic-jailbreak`、`covered`、`borderline-pressure`。
- **为什么**：10 条足够撑起「回归被抓到」的完整叙事，再多是边际收益递减而成本线性上升。砍到 3 条的额外理由是 15 RPM 的配额——3 条一跑就是 12–18 次调用，已经触顶。
- **代价**：统计意义很弱，误差区间宽得没法看。3 条更弱。
- **缓解**：UI 明示 `n=1` 并在样本不足时标注，不假装数字精确。3 条的补法不是加条数，而是**给每条加维度**——persona（暴躁 / 中性）让一条 case 同时考行为正确性和语气韧性，off-topic 那条同时考拒答、不泄露、不反弹敌意。产品的真实答案仍然是从生产 trace 里持续长测试集，而不是一开始就写一个大的（那条路的起点是 Step 3 的 Production tab）。

**存 YAML 文件，不入库**

- **决定**：数据集是一个 YAML 文件（`datasets/golden.yaml`）。**原定 XML，最终改为 YAML。**
- **为什么不入库**：数据集是**输入**，改它就是改测试标准，必须走代码评审、必须能 diff、必须和 config 一起进 git 历史。放数据库里就成了「谁在什么时候悄悄改了断言」这类问题的温床。
- **为什么最终选 YAML**：
  - **不用转义。** 三条 case 里两条是敌意问法，含 `—`、`'`、引号；XML 里 `<` `&` 要转义，YAML 里块标量（`|`）原样照抄。数据集是要**手写手改**的东西，转义规则是纯摩擦。
  - **手写期望是多行自然语言。** `expect` 的正文是一整句判据，YAML 的 `|` 块标量比 `<expect policy="P7">…</expect>` 的单行挤压好读。（原文这里写的是「一整句**中文**判据」。Step 3 把数据集全文改成英文了——它是代码交付物的一部分，评审要能读——所以这条理由的措辞过期了，但理由本身成立。）
  - `pyyaml` 一行 `safe_load` 出嵌套 dict，比 `xml.etree` 手工遍历元素、区分属性和正文省一半解析代码。
- **代价**：YAML 有它自己的坑——缩进敏感、`no` / `yes` 会被解析成布尔。所以 `tool_called.expected` 明确写 `true` / `false`，解析器对未知 key 直接崩（let it fail，[TO-22](#to-22-交付形态能一口气读完零构建跑起来)），不做容错猜测。拼错的 key 被静默忽略的话，那条断言就什么都不做了——**「写了但不跑」比没写更危险**。
- **不变的部分**：两段式结构（`observations` / `expectations`）和 persona 都跟格式无关，换格式只动 `dataset.py` 一个函数。

## D. 交付与运维

### TO-15 不做 production monitoring 和 alerting

- **决定**：**不做定时任务、趋势图、告警规则、自动报表。**
- **为什么**：时间不够，而且**这一层是商品化的**。
- **关键论点**：难的部分是**产出结构化、带 tag、带逐条 policy 判定的数据**；dashboard 和 alerting 层是现成的。只要每条 conversation 都带 experiment tag、judge 结果都是逐条 policy 判定，把 Superset / Grafana 指到同一张表，告警就只是配一条阈值规则的事。**所以我把时间花在数据模型上，而不是重新实现一个报表工具。**
- **代价**：发现问题依赖人主动去捞，没有及时性。真出事的时候不会有人半夜手动点一下 judge。
- **后续**：一个定时 job 把 judge 跑在采样流量上，加一条违规率阈值规则，就是完整的告警链路。

**Step 3 修正：连「按 tag 抽取」也砍了，改成一个只读视图**

原文说的是「只做『按 experiment tag 抽取生产对话 + 手动触发 judge 复跑』」。Step 3 把这句**再往下砍一刀**：按 tag 检索、按 arm 切片对比、把生产对话加进 golden dataset、定时复跑 judge，**全都不做**。做的是一个不带任何筛选的 **Production tab**——`GET /api/conversations?limit=30` 的结果渲染成只读表，列是 `version_label` / `config_hash` / `arm` / `experiment_tag` / `terminated_by` / 成本，点一行展开完整轨迹。

- **console UI 里原本一处 tag 都没有**（840 行，`experiment_tag` / `arm` / `rollout` 零命中）。但后端是完整的：`/api/conversations` 从 Step 1 就支持 `?tag=` 和 `?arm=`，`experiment_tag` 建了索引。缺的是**视图**，不是数据、不是端点、不是索引。
- **为什么是只读真实数据，而不是像灰度那样做禁用控件**：**因为这里有真东西可以给你看。** 灰度那边没有 `Experiment` 行，除了插一行别无办法（已否）；而生产对话是真的、每次 demo 都在增加、每一行都带着 version 和 arm 和 `config_hash`。「这些数据都已经存下来了」这句话，用一张有真实行的表说出来，和用一段文案说出来，说服力差一个量级。而它的成本是**零新后端**。
- **顺带补上一个真实的缺口**：原来演示「Activate 改变行为」靠同一个问题问两次、肉眼比较两次回答。有了这张表，两次请求以两行并列出现，`version_label` 和 `config_hash` 两列不一样——**同一个变更的前后对照变成表格里可以指的东西**。这不是新能力，是把已经落库的数据显示出来。
- **代价**：`/api/conversations` 返回整行含完整 `trajectory`，30 行是个不小的 payload。本步不改端点（不动 Step 1 已验收的代码），前端只取需要的字段。「该给列表页做一个精简投影」是已知欠账。
- **`Conversation` 存的是 `version_id` 不是 `version_label`**——label 是 console 的说法、可以改名，id 才是实际发生的事。表里的 label 是拿版本列表反查出来的，hash 无论如何都显示，因为那才是标识行为的东西。

### TO-16 seed 用预计算结果直接入库，不做 fixture replay 层

- **决定**：seed 脚本把预先算好的 conversation 和 benchmark 结果直接写进 SQLite。不实现「录制/回放 LLM 响应」的 provider 层。
- **为什么**：目的是让评审人打开就看到有数据的界面，这个目的用 seed 数据就能达到，比实现一个 replay provider 便宜得多。
- **代价**：没有 API key 就跑不了新的 run，只能浏览已有数据。
- **保留的部分**：结果缓存仍然是 P0，键为 `config_hash` + `dataset_hash` + `corpus_hash` + `case_id`。既省钱又让重跑秒出。

**Step 3 落地：交付形态是可提交的 JSON fixture + 幂等脚本，不提交 `.db`**

- **为什么不能提交 `.db`**：`data/` 在 `.gitignore` 里。而且二进制文件在 git 里没法 review，提交我自己的库等于把我问过的每一个问题一起提交。
- **形态**：`datasets/demo_seed.json`（**从真实运行导出的行，不是手写的**）+ `scripts/seed_demo.py` 的 `export` / `load` 两个模式。装的内容是两次 benchmark run（基线 3/3 绿、`bad-scope` 2/3 抓到回归）、三种终止态各一条 conversation、以及它们引用的版本。生成对话的那一步单独是 `scripts/seed_conversations.py`，**走真实的 HTTP 路径**——手工构造的行不会带 `version_id` / `config_hash` / `trajectory`，而那三样恰好是这个产品的全部内容，一份对自己来源说谎的 fixture 比没有 fixture 更糟。
- **export 只导每个 label 最新的那一次 run**。改一个 prompt 常量会改 `config_hash` 但不改 `dataset_hash`，所以同一个 label 会攒下一堆指向「代码已经产不出来的配置」的 run。把它们导进去，等于主动 ship 一批 `config_hash` 解析不到任何东西的结果——正是 `load` 会警告的那种漂移。版本同理，只导被导出的 run 和 conversation 真正指到的，加上当前 active 的那一个；否则 fixture 会带上我自己攒的全部版本历史，其中大部分什么都不说明。
- **一处刻意的空缺**：`bad-scope` 那次 run 的 `config_hash` 在版本表里没有对应行——那份配置是代码里的 `BAD_SCOPE_V2` 常量，从没被存成版本。不预存它是有意的：demo 的叙事是「有人去把范围规则改严了」，而那正是**演示时的动作**；预先烤好一个 `v2-strict-scope` 会让它看起来是安排过的。代价是无键评审没法在版本表里 diff 这两份配置，只能看到两次 run 的结果差异。
- **`load` 的语义是插入缺失行，不是 upsert**：已存在的行以数据库为准。点了半天的评审不该被罐头数据静默覆盖。
- **顺带解决三件事**：无 key 的评审能看到有内容的界面（配合 [TO-31](#to-31-model-跨-provider-可换但仍然不是版本化杠杆)）；Production tab 在 demo 开始前就有行可看；「回归被抓到」的故事不依赖当场跑 80 秒和一大截配额。
- **代价**：fixture 是某一次真实运行的快照，会和代码**漂移**——prompt 常量一改，fixture 里的 `config_hash` 就对不上任何现存 `Version`。这跟 [TO-26](#to-26-search_docs-mention-语法取代-tool_description-占位符) 处理过的是同一类问题，处理方式也一样：只增不删、幂等，`load` 时**主动比对 `dataset_hash` 并在不一致时打印警告**（一个 hash 对不上任何东西的 run 正是这个产品要消灭的漂移，得说出来而不是留给人在 UI 里发现），且 seed 出来的行在 UI 上带 `seeded` 标记，不会被误认为刚跑出来的。
- **实现时踩到的一个坑**：`model_dump_json()` 把 datetime 序列化成 ISO 字符串，而 SQLModel 的 `table=True` 类**不做构造时校验**，字符串会一路怼到 DateTime 列，然后在离原因好几帧的地方炸。修法是按字段注解还原，修在 JSON 这一侧——不能让模型去容忍它运行时根本不该见到的类型。

### TO-31 `MODEL` 跨 provider 可换，但仍然不是版本化杠杆

- **决定**：`MODEL` 支持 `gemini/`、`anthropic/`、`openai/` 三个前缀。价格表补了几个便宜型号，加了一个**启动期 key 检查**，`.env.example` 和两份 README 写明怎么换。**四个版本化杠杆一个字段都没动。**
- **为什么**：题面预置的 `.env.example` 是 Anthropic / OpenAI / ElevenLabs / Google Cloud / AWS 的 key，我们要的是 AI Studio 的 `GEMINI_API_KEY`——**不在这个名单里**（名单里的 Google Cloud 是 Vertex AI，是另一套凭据）。[TO-05](#to-05-模型这条轴整个不动) 早就写下了这个风险（「否则对方跑不起来」），但一直只停在「在文档里说明」。只在文档里写一句「请自备 Gemini key」，实际效果是：评审跑起来、问一个问题、拿到 502——**最糟的一种失败，因为它看起来是我们的 bug**。
- **工作量比看起来小**：抽象早就在了。LiteLLM 按 provider 前缀自己找环境变量，`litellm.drop_params = True` 丢掉目标模型不支持的参数。换 provider 本身已经能用，要补的只是价格、检查和文档。
- **为什么不和 [TO-05](#to-05-模型这条轴整个不动) 矛盾**：两件事一直是分开的。`MODEL` 是**部署级设置**（从 Step 1 就是环境变量），那四个杠杆是**产品级变更单位**。TO-05 说的是后者，本条动的是前者。
- **启动期检查而不是首次调用时报错**：按 `MODEL` 的前缀查对应变量在不在，不在就在**启动期**崩掉，错误信息直接点名缺哪个变量。符合 [TO-22](#to-22-交付形态能一口气读完零构建跑起来) 的取向——崩在离原因最近的地方。顺带覆盖了没听过的 provider（`cohere/...` 会明说这个项目没有它的价格和 key 映射）。
- **代价，两条，都是真的**：
  1. **新增的价格数字我没有实测过 token 计费**，只是照公开价目表抄的。所以非 Gemini 模型上的成本数字，可信度比 Gemini 那行低一档。
  2. **Anthropic / OpenAI 这两条路我一次都没跑过**——手上没有这两个 key。所以 README 和 `.env.example` 里的措辞是「wired, not verified」，**不是「支持」**。具体的风险点是结构化输出：[TO-20](#to-20-工具自己编排不用原生-function-calling) 的整个论证建立在「`responseSchema` 删掉了格式错误这一整类失败」上，如果某个 provider 只是在 prompt 里模拟 schema，那 `ValidationError` 会回来，而 [TO-22](#to-22-交付形态能一口气读完零构建跑起来) 说了格式错误直接抛。声称支持一条没跑过的路，比不声称更糟。
- **另一半缓解**：[TO-16](#to-16-seed-用预计算结果直接入库不做-fixture-replay-层) 的 seed 数据。没有任何 key 也能看到完整界面和两次真实 run 的结果。
- **已知缺口**：`MODEL` 一换，`BenchRun` 里的历史基线就不可比了——这正是 TO-05 警告过的事。`BenchRun` 应该把 `model` 记下来（现在没记），让不可比至少是**可见**的不可比。

## F. 实现选型

### TO-20 工具自己编排，不用原生 function calling

- **决定**：`search_docs` 不作为 Gemini 的 `functionDeclarations` 传给模型。`plan` 和 `reflect` 在自己的**结构化输出**（`responseSchema`）里给出 `needs_search` / `query`，由编排层执行检索。`tool_description` 仍是被版本化的杠杆，改为注入进 prompt。
- **为什么**：
  - **`responseSchema` 和 function calling 一般不能同时用**，必须二选一。
  - 结构化输出**删掉了「格式错误」这一整类失败**。这类失败在评测里特别有害，因为**它会伪装成行为回归**：改一句 prompt 后几条 case 挂了，看着像行为变差，实际只是模型多输出了一个代码块围栏。
  - prompt 里不用再写「Return JSON only: {...}」这类样板，**prompt diff 于是变成纯粹关于行为的 diff**，而不是混杂着格式管教。
  - 「要不要检索」从「有没有出现 functionCall part」这种隐含信号，变成 trace 里一个显式的布尔值，**可以直接断言**。对一个主题就是「让 AI 行为可见」的产品，这个差别很重要。
  - 顺带绕开了 Gemini 与 OpenAI 工具格式的全部差异。
- **代价**：不是常规意义上的「agent 自主调用工具」。工具从 1 个涨到 10 个时，prompt 注入描述的扩展性明显不如原生 function calling。当前只有一个工具，代价为零。
- **必须配套的一条**：`plan` 必须有权输出 `needs_search: false`。否则编排层无条件检索，**「改窄工具描述导致模型不再检索」这个高光 demo 根本无法发生**。这条在 Step 1 的验收里就验证了。
- **和 [TO-31](#to-31-model-跨-provider-可换但仍然不是版本化杠杆) 的关联**：这整套论证依赖 provider 提供**真的** `responseSchema`。换到一个只在 prompt 里模拟 schema 的 provider，格式错误就会回来。这是 TO-31 里那条「wired, not verified」的具体所指。

### TO-21 两个 app 用一个 Python 服务托管，拆分是部署决策

> 已并入 [TO-08](#to-08-代码边界与进程边界是两件事)。编号保留：共 8 处引用。原本独立成条，是因为它**修正**了 TO-08 里「两个独立服务」的说法——当时保留两条是为了让这次修正本身留下痕迹。

### TO-22 交付形态：能一口气读完、零构建跑起来

> Step 3 合并：吸收了原 TO-23（不写单测）、原 TO-24（`/chat` 前端不上构建链）、原 TO-27（console 前端不上构建链）。四条的「为什么」是同一句话，写了四遍。

- **共同的为什么，两条**：
  1. **能读懂比能扩展重要。** 这份代码要能被一口气读完。真正要展示的东西是变更管理那套东西，chatbot 越薄越好；防御性代码会把 200 行核心逻辑撑成 500 行，而多出来的 300 行没有一行在讲产品。测试文件和构建配置同理。
  2. **在干净容器里跑起来这件事，比可扩展性值钱。** 题面明确要在 fresh Linux container 里跑。没有 node_modules、没有构建步骤，Dockerfile 就是单阶段纯 Python 镜像，少一整类「评审机器上装不上」的失败模式。

**「let it fail」的错误处理：全项目只有三处**

- **决定**：默认不接错误，让它崩在原地带完整 traceback。不写 `except Exception` 兜底，不为「理论上可能为 None」加降级分支。**全项目只有三处错误处理：**
  1. **`llm.py` 的重试**——`tenacity` 只对 429 / 超时 / 5xx 退避重试。这类错误跟我们的代码无关，纯粹是对面的状态。**其余一律不重试**，4xx 是我们把请求构造错了，重试只会用同样的方式再错一次。
  2. **路由边界的落库**——一个 try 包住整次请求，写一条带 `error` 和部分 `trajectory` 的 Conversation，然后返回 502。
  3. **benchmark runner 的逐 case 隔离**——批量跑 golden case 时，一条崩掉不能带走整批，记成该 case 的 `BenchResult.error`。（原文写的是「只有两处」，Step 2 加了第三处，Step 3 把这个计数改对了。）
- **「崩」的粒度是一次请求，不是整个进程**：FastAPI 里处理函数抛异常只让那一个请求失败，进程照常服务下一个。启动期异常（语料缺失、缺 key）才是真的进程退出，那正是要的。
- **为什么第 2、3 处不算违反**：第 2 处不是在恢复，是在**观测**——它没让请求成功，只是让失败被记录，而灰度健康度和自动回滚触发器完全建立在这份记录上。**没有错误记录，就没有「这个候选版本在生产里更容易出错」这个信号**。第 3 处同理：第一条 case 崩掉顺带藏掉后两条的结果，比一行红色糟得多。
- **格式错误直接抛，不喂回 loop**：节点输出用 Pydantic 解析，`ValidationError` 原样上抛。**明确不做「把错误信息拼回 prompt 让模型自我纠正」。** 上了 `responseSchema`（[TO-20](#to-20-工具自己编排不用原生-function-calling)）之后格式错误已近乎不可能，真发生了说明是 schema 被拒或 SDK 变了这类真 bug——**自动重试只是在用同样的姿势烧配额**，还会把一个该立刻暴露的 bug 变成「偶尔慢一点」的怪现象。
- **代价**：用户偶尔撞到 502 而不是一个降级的答案；崩溃点分散在各处，没有统一的错误分类。可以接受——**失败是可见、可记录、可被统计的失败，比一个偷偷降级的假答案诚实得多。**

**不写单元测试，只留一个冒烟脚本**

- **决定**：不写 pytest 测试套件。原设计里的 `test_search.py` / `test_graph_loop.py` / `test_no_cross_app_imports.py` 全部取消。保留 `smoke.py`：跑几个真实问题，把轨迹打出来，人眼确认行为对不对。
- **为什么**：这是个 demo，不是要长期维护的 production system。**单测的价值在于「改动时防回归」，而这个项目的整个主题恰恰是「用 benchmark 来防 AI 行为回归」**——golden dataset + judge 就是这个项目版本的回归测试，再写一层 pytest 是重复投入，而且投在了不是考点的地方。
- **代价**：`search.py` 的打分逻辑和分桶函数这类纯函数，本来单测很便宜、收益也实在；现在它们出错只能靠冒烟时肉眼发现。
- **但机制类的东西补回来了**：`scripts/check_assertions.py` 不测产品行为，测**断言机制本身**——工具改名会不会被抓、字面 `{` 会不会崩、`passed` 会不会被 verdict 污染、两个 app 有没有互相 import、单 case 报错会不会带走整批。每条检查都构造一个**应该 fail** 的输入去验它真的会 fail（理由见 [TO-30](#to-30-引用检查用贪心最长匹配不按分隔符切分)）。这是从「不写测试」里挑出来的、唯一值得写的那一类。

**前端不上构建链，两个页面都一样**

- **决定**：放弃原定的 Vite + React + Tailwind + shadcn/ui，两个页面都是手写静态文件（原生 JS + 手写 CSS），由 FastAPI 的 `StaticFiles` 直接托管。视觉 token 仍照 [TO-18](#to-18-前端往-anthropic-claude-的设计风格做) 走。
- **`/chat` 的理由**：页面上只有一个输入框、一段回答、一个 thinking 指示、几个引用 chip 和一个折叠面板。用不上组件库，也用不上构建工具。
- **`/console` 的理由（Step 2 重新确认过一次）**：console 信息密度高得多——版本列表、四个带 `#` 补全的 prompt 编辑器、三个 tab、结果表、词级 diff。但仍在手写能 hold 住的范围内，而「干净容器里零构建跑起来」的价值在页面更多的场景下**比 Step 1 更大**：构建链一旦在评审机器上装不上，损失更大。
- **代价**：`#` 自动补全、tab 切换、词级 LCS diff、结果表这些要手写，比用组件库累。最终 console 前端约 1000 行。
- **推翻条件**：如果交互复杂到手写明显拖慢进度，退路是 CDN 上的 React（仍无构建链），而不是整套 Vite + shadcn。
- **不打折的部分**：视觉质量不因为手写就降级。

### TO-25 Simulation 只单跑，不并排对比基线

- **决定**：Simulation tab 只展示草稿配置这一趟 3 条 case 的结果和逐条 policy 判定，**不在同一屏并排显示当前生效版本的结果**。
- **为什么**：并排对比要多跑一趟基线（吃配额，15 RPM 约束）并多做一个 diff 视图。重心是把「接进数据库的 benchmark 能跑起来」做扎实，对比是锦上添花。
- **代价**：这直接损伤了 [TO-10](#to-10-评测输出的形状逐条判定确定性做门禁judge-只做参考) 的核心论点——「case 3 的 P3 **从 pass 翻成 fail**」比「case 3 的 P3 是 fail」可行动，而单跑只能看到后者。演示回归时要靠人先跑基线、再跑候选，两屏对照。
- **缓解**：所有结果以 `config_hash` 为键落 `BenchResult`。以后加「vs 当前生效版本」的并排视图，只是多一个读两次结果做 diff 的页面，不用改数据模型、不用重跑。Step 3 的 seed 数据里就装了这两次 run（基线 3/3、`bad-scope` 2/3），对比所需的数据已经在库里了，缺的只有那个页面。
- **边界**：[TO-10](#to-10-评测输出的形状逐条判定确定性做门禁judge-只做参考) 的「翻转重跑」也一并推迟——它本质是跨 run 比对，属于对比的范畴。

### TO-26 `#search_docs` mention 语法取代 `{tool_description}` 占位符

- **决定**：prompt 里引用工具从 Python 的 `{tool_description}` 占位符（`str.format()` 展开）改成 `#search_docs`（正则 `#(\w+)` 替换展开），工具名→杠杆的映射放在 `TOOL_REGISTRY`，工具名本身只由 `packages/agent/search.py` 的 `TOOL_NAME` 常量定义。
- **为什么**：
  - **UI 能力**：prompt 变成 console 里的自由文本后，`#` 可以挂自动补全、把工具引用渲染成能溯源到具体杠杆的 chip。
  - **修 bug**：`str.format()` 遇到用户在自由文本里打的字面 `{` / `}` 会抛 `KeyError`，且崩在跟输入毫无关联的 `plan.run()` 里。正则替换对花括号无感，整类转义问题消失。这跟 [TO-22](#to-22-交付形态能一口气读完零构建跑起来) 不冲突——let-it-fail 是不兜真实错误，不是留一个正常输入就能触发的雷。
  - **一个工具名贯通三处**：prompt 里的 `#search_docs`、轨迹里 search 节点的 `tool` 字段、golden case 里的 `tool_called.name`。全部引同一个常量，改名时 benchmark 断言会**报错**而不是静默永远 pass。
- **为什么是 `#` 而不是 `@`**：引起上面那个 bug 的是 `str.format()`，跟符号无关，两个符号都能修掉，所以纯粹是约定选择。`#` 的三种潜在冲突都不成立，实测逐条验过：markdown 标题（`# Rules`）后面有空格不匹配；编号引用（`#1`、`#2`）匹配到但不在注册表里、原样透出；`C#` 这类也原样透出；现有四段 prompt 常量里没有 `#`。「未注册的名字原样透出」这条兜住了所有意外匹配。
- **代价**：`config_hash` 会因 prompt 常量改写而变。原本打算重新 `init-db`，实现时改成了**不删任何东西**：`seed_baseline()` 改为幂等自愈——发现当前 `BASELINE_V1` 的 hash 不是 active，就把旧的 active 标成 `archived`、把它插进去并激活。理由是「active 版本的 hash 对不上源码里任何 config」正是这个产品要消灭的那种不可见漂移，而删表既解决不了这个问题、又会把已有的对话和评测历史一起带走。
- **展开范围**：`expand_tools()` 对四个 prompt 杠杆**一律**生效，不只 `plan_prompt`。四个都是 console 里的自由文本，只有一个能用 mention 会变成一条要记住的例外；对不含 mention 的 prompt 它是零成本 no-op。
- **边界**：当前只有一个工具，补全菜单只有一项。不为了菜单「显得丰富」去加工具。

### TO-29 golden case 的问法用探针脚本挑，不靠手写

- **决定**：`covered` 这条 case 的问法不是想出来的，是用两个探针脚本筛出来的：`scripts/probe_scope.py`（只调 plan 节点，判「基线 in scope 且严格版 out of scope」）和 `scripts/probe_stability.py`（重复采样，判 `terminated_by` 稳不稳）。定稿后的问法和筛选理由都写在 `datasets/golden.yaml` 的注释里。
- **为什么**：Step 2 实现时第一版手写的问法看起来完全符合「概念性、不点名功能」的要求，**结果 `BAD_SCOPE_V2` 三条全 pass——回归从整个数据集旁边走过去了**。一个「全绿但其实什么都没在防」的数据集，比没有数据集更危险，因为它会让人相信自己有防护。这条 case 同时要满足两个互相拉扯的条件（基线稳定通过、严格版必须误拒），靠直觉判断达不到。
- **为什么用只调单节点的探针，而不是整批重跑**：一个候选问法在 plan 探针下花 2 次请求，跑一整对 case 要 8–12 次。免费额度 15 RPM，这个差别直接决定了「能不能试 7 个候选」还是「只能试 1 个」。
- **代价**：多了两个脚本，而且 golden case 的问法从此**跟 `BAD_SCOPE_V2` 这个具体配置耦合**了——换一个 regression 配置，`covered` 的问法可能要重挑。这个耦合是显式的（写在 YAML 注释里），不是隐藏的。
- **副产品**：这件事本身就是产品主张的演示——**用这个 benchmark 工具挑选它自己的测试用例**。值得写进 `APPROACH.md` 和视频。

### TO-30 引用检查用贪心最长匹配，不按分隔符切分

- **决定**：`cites_real_article` 的判法是「把能找到的真实标题按长度倒序逐个从 `Source:` 行里抠掉，剩余文本必须为空」，而不是按逗号 / `and` 切开逐段查表。
- **为什么**：真实标题里就带这两个分隔符——`Run, Edit and Share Skills`、`Ray 3.2 Prompting, Outputs & Controls`、`Character and Object Consistency`。切分会把合法标题碎成片段，而片段又因为子串包含**碰巧匹配上**。第一版实跑输出的是 `cited ['Character', 'Object Consistency', ...]`：检查显示绿色，但**它是因为错误的原因而通过的**，跟坏掉没有区别。
- **代价**：最长匹配是 O(标题数 × 文本长度)，39 篇文章的规模下无所谓；语料大到几千篇要换成 Aho-Corasick。
- **一般化的教训**：确定性检查的危险失效模式不是「误报」而是**「因为错误的原因通过」**。误报会被人看见，后者不会。所以每写一条检查，都要构造一个应该 fail 的输入去验它真的会 fail——`scripts/check_assertions.py` 存在的理由。
