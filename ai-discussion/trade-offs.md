# Trade-offs

活文档，随做随记。每条一个稳定编号，plan 和最终的 `APPROACH.md` 都直接引用编号。

格式统一为：**决定 / 为什么 / 代价 / 缓解或后续补法**。

---

## A. 产品范围

### TO-01 对话是单轮的，但内部轨迹是多步的

这两件事必须分清，否则看起来自相矛盾。

- **决定**：
  - **对话单轮**：用户视角只有一问一答，不保留跨轮历史。
  - **内部多步**：一次请求内部是一个 ReAct 循环，`plan → search → reflect → …（≤3 轮）→ synthesize`。
- **为什么单轮对话**：评测单元因此极简——一个输入对应一个可判定的输出。多轮对话的评测要评「跨轮上下文是否被正确继承」，是另一个产品。
- **为什么内部多步**：单跳检索答不了需要两处证据的问题；而且显式的多节点结构带来三个评测上的收益——每个节点的 prompt 可独立版本化、policy 违规可归因到具体节点、`max_loops` 成为一个真实的成本/质量权衡杠杆（补回了 [TO-05](#to-05-模型不可配置全系统固定一个便宜模型gemini-flash) 砍掉的那条轴）。
- **代价**：每个问题的 LLM 调用从 2 次涨到 3–5 次，**配额压力和端到端延迟都翻倍**；Step 1 预算从 2 小时涨到 2.5 小时；Step 2 必须支持对**轨迹**下断言（循环次数、是否检索过、`terminated_by`），不只是对最终文本下断言。
- **仍然的缺口**：跨轮对话的行为漂移看不见。这仍是本项目最大的能力缺口，只是「单次请求内的多步轨迹」这一半已经补上了。

### TO-02 检索用 grep，不做 RAG

- **决定**：`search_docs` 就是对本地文件的关键词检索，无 embedding、无向量库、无 reranker。
- **为什么**：检索质量不是本项目的题目，change safety 才是。做 RAG 会引入一整套不同的评测词汇（recall@k、chunk 归因），把时间吃光还模糊了主线。
- **代价**：召回明显差，概念性问题经常检索不到好片段。
- **这个代价反过来是收益**：检索不到时模型是否老实说「不知道」，正好是 P3（Refusal）最好的考场。而且 grep 弱 ⇒ 工具描述对模型行为的影响被放大 ⇒ TO-06 那个 demo 更有说服力。

### TO-03 语料是本地静态快照

- **决定**：一次性抓取 Luma Learning Center 的 38 篇文章存成本地 markdown，之后不再更新。
- **为什么**：语料新鲜度与本项目无关，且离线可复现对评审更友好。
- **代价**：不做增量更新、不做失效检测。文档改版后我们的答案会过时而系统不自知。

### TO-04 不做认证、多租户、RBAC

- **决定**：假设单团队单用户，没有登录。
- **代价**：不能演示「谁改了什么需要谁批准」这类真实的变更治理。审计日志仍然记录 actor 字段，只是值是硬编码的。

## B. 架构与运行时

### TO-05 模型不可配置，全系统固定一个便宜模型（Gemini Flash）

- **决定**：`model` **不进**版本化配置。chatbot 和 judge 都用 **Gemini Flash**（Google Generative Language API），写在 `.env` 里。
- **为什么**：demo 用我个人的 Gemini API key，成本自己承担，所以选最简单最便宜的模型。另外 judge 模型本来就**必须** pin 住——judge 模型一换，历史基线全部失效，评测就没有可比性了。
- **两个衍生决定**（详见 [design_step1_ai_app.md](design_step1_ai_app.md) 第 5 节）：
  - **`.env` 里填具体版本号，不用 `gemini-flash-latest` 别名**，并把响应里的 `modelVersion` 记进每条 trace。别名会漂，而漂移会伪装成「我的 prompt 改动导致了行为变化」，是所有风险里最难排查的一种。
  - **成本用本地价格表算，不用 LiteLLM 的 `completion_cost()`**。别名或新模型查不到价格会静默返回 0，而成本是高光 demo 的一半说服力。既然模型已 pin，价格表只有两个数字。
- **对评审的影响**：题面预置的 `.env.example` 是 Anthropic/OpenAI 的 key，我们用 Gemini，所以 README 和 APPROACH.md 必须显著说明需要自备 Gemini key，否则对方跑不起来。
- **代价**：失去「换个便宜模型」这条现实中最常见的行为变更动机，成本轴的变化幅度也变小了。
- **但保留了什么**：成本和延迟仍然是一等公民指标，因为**是否调用检索工具本身就显著影响成本和延迟**。这反而让 TO-06 的 demo 更漂亮：模型不检索之后，成本降了、延迟降了、答案还很流畅——**看起来像一次优化，实际是一场灾难**。这比换模型省钱的故事更有冲击力。
- **后续**：配置对象里加回 `model` 字段即可，评测/审阅/灰度/回滚流水线一行都不用改。

### TO-06 被版本化的杠杆是六个

- **决定**：版本 = `plan_prompt` + `reflect_prompt` + `synthesize_prompt` + `tool_description` + `temperature` + `max_loops`。`config_hash` 是全部六项规范化后的 sha256。存成一个 JSON 列而不是六个字段，这样加杠杆不用改表。
- **为什么**：题面列的七个杠杆想说的是「变更单位是一份行为配置，不是一段 prompt」。
  - **三个节点的 prompt 分别版本化**，而不是拼成一个大 prompt——这是 diff 可归因的前提，断言失败时能直接指出该改哪个节点。
  - **`tool_description` 纳入版本**是让产品不退化成 prompt 管理工具的关键，而且它解锁了本项目最强的 demo：**改一行工具描述，模型就不再检索、开始凭空编造，而 prompt 的 diff 是空的**。
  - **`max_loops` 是一个数值杠杆**，调低更便宜更快但 `exhausted` 率上升，调高召回更好但成本延迟线性上升。这是教科书级的需要人来判断的权衡，也补回了 TO-05 砍掉的成本/质量轴。
- **代价**：版本对象比原来大得多，diff UI 必须按节点分组渲染，否则一屏塞不下。杠杆里仍然没有 model / retrieval / post-processing。
- **缓解**：在 APPROACH.md 里说清楚流水线对变更类型不可见，加杠杆是加字段而不是改架构。

### TO-07 prompt 放在 critical path 上

- **决定**：生效版本的解析放在**线上请求路径里**。chatbot 每次请求都通过 `config_client` 拿当前该用哪个版本，绝不把 prompt 编译进代码或从静态文件读死。
- **为什么**：**这是能做 gradual traffic rollout 和即时回滚的唯一前提。** 如果 prompt 写死在代码里，切流量就必须重新部署一次，实验根本没法做，「一点一点放量」这个核心能力就不存在。
- **代价**：控制平面成了业务的**运行时依赖**——每个请求多一次配置读取，并且多了一类故障模式（配置读不到就服务不了）。
- **缓解**：进程内 5 秒 TTL 缓存，加上 console 写操作调用 `invalidate()` 让改动立即生效。
- **原本还有 fail-open 到 last-known-good，现在去掉了**（见 TO-22）：合并成单进程之后这只是一次本地 SQLite 读，没有「只有配置挂了」这个故障模式，那个分支是永远跑不到的死代码；而且**配置读失败时静默沿用旧配置，恰好制造了这个产品要消灭的那种情况**——行为和你以为的不一致且毫无信号。**以后真拆成两个进程、这一跳变成 HTTP 调用时，fail-open 就该加回来。**
- **明确不做**：分布式配置中心、配置 CDN、多 region 一致性。

### TO-08 两个 app 共享一个 SQLite，契约提到共享包里

> 进程数已改为「默认合并成一个服务」，见 TO-21。本条保留的是**代码边界**的部分。

- **决定**：`apps/chatbot` 和 `apps/console` 是两个独立的代码单元，共享 `data/app.db` 一个 SQLite 文件。两者都依赖 `packages/behavior_core`，**互相不依赖**。
- **为什么需要共享包**：chatbot 需要「当前该用哪个版本」和「怎么写 trace」，而版本和实验是 console 的概念。如果这些定义住在 `apps/console/` 里，chatbot 就得反向依赖 console——**服务端依赖控制台，方向完全错了**。把契约提到 `packages/behavior_core`，方向就对了，而且它就是 TO-07 说的那个 SDK 接缝的实体：现在 `config_client` 读同一个 SQLite，生产里换成 HTTP 加磁盘缓存，chatbot 代码一行不用改。
- **代价**：
  - 两个进程并发写同一个 SQLite 会撞锁。缓解：开 WAL + 设 `busy_timeout`。demo 规模下冲突概率很低，但必须显式处理而不是撞上了才发现。
  - 配置解析走的是**数据库读**而不是对 console 的 HTTP 调用，所以「控制平面整个挂掉、chatbot 还活着」这个场景没法真正演示（数据库是两者共同的依赖）。
- **用测试守住依赖方向**：`test_no_cross_app_imports.py` 扫 `apps/chatbot/` 下的 import，出现 `apps.console` 就失败。规则写在文档里会被忘记，写成测试不会。

### TO-09 灰度按 session_id 确定性分桶

- **决定**：`hash(session_id) % 100 < rollout_pct` 决定走哪个版本。同一 session 始终看到同一版本。
- **为什么**：避免同一用户在两个版本间抖动；同时分桶函数是纯函数，可以直接写单元测试。
- **代价**：不做统计显著性检验。几十条流量下那个 p 值没有任何意义，假装有反而是误导。
- **缓解**：UI 上明示每个 arm 的 n，样本不足时直接标注，不给出「哪个更好」的结论。

## C. 评测方法

### TO-10 judge 输出逐条 policy 判定，不输出总分

- **决定**：LLM judge 返回结构化 JSON，对六条 policy 各给一个 pass/fail 加理由。**不产出 0-1 总分，不做平均。**
- **为什么**：`0.82 → 0.85` 不告诉你任何事，而「case 3 的 P3 从 pass 变成 fail，理由是编造了一个不存在的导出格式」直接可行动。平均分还会把致命违规稀释掉。
- **代价**：没法一眼比较两个版本「谁总体更好」，必须看 diff。**这正是想要的效果**——上线决策本来就不该被压缩成一个数字。

### TO-11 确定性检查优先，judge 只兜底

- **决定**：能用规则判的绝不调 judge。P2 引用用「是否包含真实存在的文章标题」匹配，P5 用词数，P6 用 system prompt 片段匹配，外加一条**「这次到底检索了没有」**的确定性断言（读 trace 里的 `plan.needs_search`，见 TO-20）。只有 P1 grounding 和 P4 拒答是否恰当交给 judge。
- **为什么**：便宜、快、可复现，而且规则类断言可以设成 blocking 门禁而 judge 不行（见 TO-12）。
- **代价**：规则会有假阴性（换一种引用写法就匹配不上）。
- **缓解**：引用匹配基于真实文章标题表做模糊匹配，而不是要求固定格式。

### TO-12 judge 本身非确定性，只对翻转的 case 重跑

- **决定**：judge 分数会抖。只对**发生 pass↔fail 翻转**的 case 重跑 k 次取多数，UI 上标注置信度低。judge 类断言默认不作为 blocking 门禁。
- **为什么**：全量多次采样太贵太慢，而真正需要确认的只有翻转的那几条。
- **代价**：非翻转 case 的判定只有单次采样，可能藏着噪声。
- **后续**：人工标注 20 条，度量 judge 与人的一致率——一致率低就不该信它的分。

### TO-13 只有 10 条 golden case

- **决定**：golden dataset 就 10 条，覆盖六条 policy 加三个幻觉陷阱。
- **为什么**：10 条足够撑起「回归被抓到」的完整叙事，再多是边际收益递减而成本线性上升。
- **代价**：统计意义很弱，误差区间宽得没法看。
- **缓解**：UI 明示 n 并在样本不足时标注，不假装数字精确。产品的真实答案是从生产 trace 里持续长测试集，而不是一开始就写一个大的。

### TO-14 golden dataset 存 XML

- **决定**：数据集是一个 XML 文件，不入库。
- **为什么**：按你的要求。它的真实优点是嵌套断言（`<expect>` 里挂多个断言元素）读起来清楚。
- **代价**：问题文本里的特殊字符要转义，手改比较啰嗦。
- **我的偏好**：YAML（同样纯文本可读可 diff，但无闭合标签无转义）。这条随时可以推翻，改动成本只有一个解析函数。

## D. 交付与运维

### TO-15 不做 production monitoring 和 alerting

- **决定**：只做「按 experiment tag 抽取生产对话 + 手动触发 judge 复跑」。**不做定时任务、趋势图、告警规则、自动报表。**
- **为什么**：时间不够，而且**这一层是商品化的**。
- **关键论点**：难的部分是**产出结构化、带 tag、带逐条 policy 判定的数据**；dashboard 和 alerting 层是现成的。只要每条 conversation 都带 experiment tag、judge 结果都是逐条 policy 判定，把 Superset / Grafana 指到同一张表，告警就只是配一条阈值规则的事。**所以我把时间花在数据模型上，而不是重新实现一个报表工具。**
- **代价**：发现问题依赖人主动去捞，没有及时性。真出事的时候不会有人半夜手动点一下 judge。
- **后续**：一个定时 job 把 judge 跑在采样流量上，加一条违规率阈值规则，就是完整的告警链路。

### TO-16 seed 用预计算结果直接入库，不做 fixture replay 层

- **决定**：seed 脚本把预先算好的 conversation 和 benchmark 结果直接写进 SQLite。不实现「录制/回放 LLM 响应」的 provider 层。
- **为什么**：目的是让评审人打开就看到有数据的界面，这个目的用 seed 数据就能达到，比实现一个 replay provider 便宜得多。
- **代价**：没有 API key 就跑不了新的 run，只能浏览已有数据。
- **风险评估**：可接受，但注意我们用的是 Gemini（[TO-05](trade-offs.md)），评审需要自备 Gemini key 而不是题面预置的那些。
- **保留的部分**：结果缓存仍然是 P0（键为 `config_hash` + case id），既省钱又让重跑秒出。

## E. 前端与交互

### TO-17 loop 期间只显示一个 thinking 指示，不显示在 think 什么

- **决定**：请求进行中前端只显示一个统一的 thinking 指示（Claude 风格的呼吸动画文字），**不做逐步进度**——不显示「正在第 2 轮检索 xxx」。因此 `/api/chat` 保持普通的请求/响应，**不引入 SSE 或任何流式协议**。
- **为什么**：
  - 这是个简单 app，不值得为进度可见性引入一套流式协议（服务端事件流 + 客户端状态机 + 中断处理）。
  - **轨迹在答案返回后已经完整可见**（`design_step1_ai_app.md` 第 9 节那个折叠面板），实时进度是重复信息，只是提前了几秒。
- **代价**：ReAct 最坏 5 次串行 LLM 调用，等待可能到 6–8 秒，期间用户完全不知道系统在做什么，可能以为卡死了。**这是整个 Step 1 里唯一一处明知体验有损而选择不修的地方。**
- **缓解（全部纯客户端，零后端成本）**：thinking 旁显示已用秒数；超过 10 秒把文案换成「还在查文档」；硬超时并给明确错误和重试。
- **顺带定案**：这条关掉了一个待议项。ReAct 把等待拉长之后我曾判断流式的价值上升了，现在明确不做。
- **区分清楚**：**等待期间不显示细节 ≠ 不记录细节。** 完整轨迹照旧落库、照旧在答案后可展开，Step 2 的全部评测都建立在它上面。

### TO-18 前端往 Anthropic Claude 的设计风格做

- **决定**：暖白纸感背景、衬线标题配无衬线正文、陶土橙作唯一强调色、大留白、几乎无阴影无边框。模型回答**不套气泡**，就是流动的正文。token 定义在 `design_high_level.md` 第 8 节，两个页面共用。
- **为什么**：一是这个气质本身适合「读文档、看诊断」这类需要长时间阅读的界面；二是 Step 2 的 diff 页面信息密度很高，冷灰蓝的 SaaS 面板风格会让它看起来更吵。
- **代价**：shadcn/ui 的默认主题是冷调 zinc/slate，要重写一遍 CSS 变量。成本不高（shadcn 本来就是靠变量做主题的），但不是零。
- **要守住的一条**：强调色只用在真正需要行动或警示的地方。到处都是强调色就等于没有强调色。

### TO-19 只有三个 API 端点，语料目录不对前端开放

- **决定**：`POST /api/chat`、`GET /api/conversations`、`GET /api/health`，没有别的。**去掉了 `GET /api/corpus/articles`。** 引用信息（`citations: [{title, url}]`）跟着 chat 的响应一起返回。
- **为什么**：检索到的文章是喂给 LLM 的上下文，不是产品要给用户浏览的目录。前端能列出全部语料，等于承诺了一个我们并不打算做的功能。这跟 TO-17 是同一个取向：**对外只暴露结果，不暴露过程和素材。**
- **不冲突的地方**：引用仍然显示。引用是答案的一部分（P2 policy 明确要求给出出处），跟「提供语料浏览功能」是两回事。
- **代价**：用户不能自己翻文档，答案里的引用是唯一入口。对一个问答产品这是合理的形态。
- **`/api/conversations` 为什么留着**：chat 前端刷新后靠 `session_id` 恢复历史，console 靠 `tag`/`arm` 做实验切片，一个端点两种用途。

## F. 实现选型

### TO-20 工具自己编排，不用原生 function calling；plan/reflect 用结构化输出

- **决定**：`search_docs` 不作为 Gemini 的 `functionDeclarations` 传给模型。`plan` 和 `reflect` 在自己的**结构化输出**（`responseSchema`）里给出 `needs_search` / `query`，由编排层执行检索。`tool_description` 仍是被版本化的杠杆，改为注入进 prompt。
- **为什么**：
  - **`responseSchema` 和 function calling 一般不能同时用**，必须二选一。
  - 结构化输出**删掉了「格式错误」这一整类失败**。这类失败在评测里特别有害，因为**它会伪装成行为回归**：改一句 prompt 后几条 case 挂了，看着像行为变差，实际只是模型多输出了一个代码块围栏。
  - prompt 里不用再写「Return JSON only: {...}」这类样板，**Step 2 的 prompt diff 于是变成纯粹关于行为的 diff**，而不是混杂着格式管教。
  - 「要不要检索」从「有没有出现 functionCall part」这种隐含信号，变成 trace 里一个显式的布尔值，**可以直接断言**。对一个主题就是「让 AI 行为可见」的产品，这个差别很重要。
  - 顺带绕开了 Gemini 与 OpenAI 工具格式的全部差异，包括并行工具调用支持到什么程度这个未知数。
- **代价**：不是常规意义上的「agent 自主调用工具」。工具从 1 个涨到 10 个时，prompt 注入描述的扩展性明显不如原生 function calling。当前只有一个工具，代价为零。
- **必须配套的一条**：`plan` 必须有权输出 `needs_search: false`。否则编排层无条件检索，**「改窄工具描述导致模型不再检索」这个高光 demo 根本无法发生**。这条要在 Step 1 的验收里就验证（清单 4c），不能拖到 Step 2 才发现模型死活不肯说 false。

### TO-21 两个 app 用一个 Python 服务托管，拆分是部署决策

- **决定**：`apps/chatbot` 和 `apps/console` 目录分开、包边界分开、依赖规则由测试守住，但**默认由一个 FastAPI 进程同时挂载**。每个 app 各自导出标准的 ASGI app，合并入口只有十几行。
- **为什么**：
  - **回滚能真正即时生效。** 两个进程时 console 改了版本没法让 chatbot 的进程内缓存失效，回滚要等最多 5 秒 TTL；合并后「点回滚 → 下一个请求就是老版本」。**这是 demo 里体感差别最明显的一处。**
  - 消掉 SQLite 多进程写竞争（WAL 仍然开着，因为分开跑仍是被支持的部署方式）。
  - 评审只需要一个容器、一个端口、一条命令。
- **代价**：没有进程级故障隔离，console 崩了会连带 chatbot。
- **为什么这个代价可接受**：**拆分只需要改部署配置，不需要改代码**——两个独立入口本来就存在，Step 1 用的就是 chatbot 那个。真需要隔离时随时能拆。
- **修正了**：TO-08 里「两个独立服务」的说法。代码边界那部分仍然有效。

### TO-22 「let it fail」的编码风格，全程只有两处 try

- **决定**：默认不接错误，让它崩在原地带完整 traceback。不写 `except Exception` 兜底，不为「理论上可能为 None」加降级分支，不给配置读取、语料加载、数据库写入包 try。**全程只有两处错误处理：**
  1. **`llm.py` 的重试**——`tenacity` 只对 429 / 超时 / 5xx 退避重试（最多 3 次）。这类错误跟我们的代码无关，纯粹是对面的状态。**其余一律不重试**，4xx 是我们把请求构造错了，重试只会用同样的方式再错一次。
  2. **路由边界的落库**——一个 try 包住整次请求，写一条带 `error` 和部分 `trajectory` 的 Conversation，然后返回 502。
- **为什么**：**这份代码要能被一口气读完。** 真正要展示的东西在 Step 2，chatbot 越薄越好。防御性代码会把 200 行的核心逻辑撑成 500 行，而多出来的 300 行没有一行在讲产品。
- **「崩」的粒度是一次请求，不是整个进程**：FastAPI 里处理函数抛异常只让那一个请求失败，进程照常服务下一个。所以不存在「一个坏问题把服务打死」。启动期异常（语料缺失）才是真的进程退出，那正是要的。
- **为什么第 2 处不算违反**：它不是在恢复，是在观测。它没让请求成功，只是让失败被记录——而 Step 2 的 Rollout 健康度和自动回滚触发器完全建立在这份记录上。**没有错误记录，就没有「这个候选版本在生产里更容易出错」这个信号**，那正是灰度放量存在的意义。所以它服务的是产品能力，不是代码健壮性。
- **格式错误直接抛，不喂回 loop**：节点输出用 Pydantic 解析，`ValidationError` 原样上抛。**明确不做「把错误信息拼回 prompt 让模型自我纠正」。** 除了简洁，还有一条更硬的理由：上了 `responseSchema`（TO-20）之后格式错误已近乎不可能，真发生了说明是 schema 被拒或 SDK 变了这类真 bug——**自动重试只是在用同样的姿势烧配额**，还会把一个该立刻暴露的 bug 变成「偶尔慢一点」的怪现象。
- **和 TO-20 互相加强**：结构化输出让「抛」的代价几乎为零，「抛」又让结构化输出真出问题时立刻可见。
- **连带删掉了 TO-07 的 fail-open**：单进程下那是永远跑不到的死代码，而且静默沿用旧配置正好制造了这个产品要消灭的那种情况。
- **代价**：用户偶尔撞到 502 而不是一个降级的答案；崩溃点分散在各处，没有统一的错误分类。可以接受——**失败是可见、可记录、可在 Step 2 里被统计的失败，比一个偷偷降级的假答案诚实得多。**
- **边界**：这条只管 Step 1 的 chatbot 和 Step 2 的 console。**Step 2 的 benchmark runner 是例外**——批量跑 10 条 case 时，单条崩掉不能带走整批，那里需要按 case 隔离错误并把失败记成该 case 的结果。

### TO-23 不写单元测试，只留一个能跑起来的冒烟脚本

- **决定**：不写 pytest 测试套件。原设计里的 `test_search.py` / `test_graph_loop.py` / `test_no_cross_app_imports.py` 全部取消。只保留一个 `smoke.py`：跑几个真实问题，把轨迹打出来，人眼确认行为对不对。
- **为什么**：这是个 demo，不是要长期维护的 production system。**单测的价值在于「改动时防回归」，而这个项目的整个主题恰恰是「用 Step 2 的 benchmark 来防 AI 行为回归」**——golden dataset + judge 就是这个项目版本的回归测试，再写一层 pytest 是重复投入，而且投在了不是考点的地方。
- **顺带的一致性**：TO-22 说代码要能一口气读完，测试文件同理。少 300 行测试代码，评审读起来更快。
- **代价**：`search.py` 的打分逻辑和分桶函数这类纯函数，本来单测很便宜、收益也实在；现在它们出错只能靠冒烟时肉眼发现。接受，因为它们都很短。
- **保留的部分**：`smoke.py` 必须覆盖第 12 节验收清单里的关键路径（正常作答、拒答、多跳、坏版本 `needs_search` 翻转），因为**那几条不是在测代码，是在验证产品行为和 Step 2 的地基**。

### TO-24 前端不上构建链，一个静态页面直接交给 FastAPI

- **决定**：放弃原定的 Vite + React + Tailwind + shadcn/ui，改成一个手写的静态页面（原生 JS + 手写 CSS），由 FastAPI 的 `StaticFiles` 直接托管。视觉 token 仍然照 TO-18 的 Claude 风格走。
- **为什么**：
  - 这个页面上只有一个输入框、一段回答、一个 thinking 指示、几个引用 chip 和一个折叠面板。**用不上组件库，也用不上构建工具。**
  - **交付更稳**：题面要求在干净 Linux 容器里跑起来。没有 node_modules、没有构建步骤，Dockerfile 就是单阶段的纯 Python 镜像，少一整类「评审机器上装不上」的失败模式。
  - 符合 TO-22 / TO-23 的同一个取向：能读懂比能扩展重要。
- **代价**：Step 2 的 console 信息密度高得多（diff 表格、benchmark 结果、放量控制），手写会比 React 累。到那时再决定要不要引入，**但即使引入也应该是 CDN 上的 React 而不是一套构建链**。
- **不打折的部分**：视觉质量不因为手写就降级。TO-18 那套 token 照样实现。
